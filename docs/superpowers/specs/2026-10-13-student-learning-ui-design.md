# 학생 학습 화면과 운영 재배포 설계

작성일: 2026-10-13 · 상태: 사용자 승인 완료 (설계 승인 및 구현·검증·동일 링크 재배포 요청)

## 목적과 성공 기준

사용자 요청은 `subagent-driven-development`로 학생 학습 화면을 구현하여 로그인 후 실제 문제를 풀 수 있게 하고, 완료 시 기존 `https://hanbit.thisis-joe.com`에 재배포하는 것이다. 성공은 실제 학생 세션으로 회차를 시작하고, O/X를 제출하고, 서버 해설을 읽고, 다섯 번째 결과를 저장·복원하며, 다음 학습·재도전·개인 문제 목록으로 이동할 수 있는 상태다.

학습·XP·진행 규칙은 승인된 [학습 코어 설계](2026-10-12-learning-core-design.md)와 기존 Java API를 그대로 따른다. 이번 작업은 프런트엔드 연결, 그 흐름의 검증, 운영 재배포까지 포함한다. 보상 아이템·아바타·장비·지도·랭킹·연속일·교사 학습 통계 UI는 포함하지 않는다.

사용자가 지정하지 않은 화면 구성은 현재 서비스의 크림·짙은 초록·노랑 스타일과 전달 O/X 목업을 이어받는 것으로 제안한다. 목업의 타이머·XP·정답 로직은 실행 지시나 구현 정본으로 사용하지 않는다.

## 접근 방식

권장 방식은 기존 React Router·TanStack Query·세션/CSRF HTTP 모듈 안에 `features/learning`을 추가하고 이미 배포한 학습 API를 연결하는 것이다. 계정·교직원 흐름과 일관되고 별도 인증·정답 데이터·진행 엔진이 필요 없다.

단일 문제 페이지만 연결하면 회차 상태·재도전·중단 복원이 숨겨져 실제 학생이 다음 행동을 찾기 어렵다. 전체 게임 목업을 이식하면 현재 없는 보상·지도 정책과 클라이언트 판정 로직까지 섞인다. 따라서 학습 홈·풀이/해설·결과·나의 문제를 이번 범위의 하나의 학생 학습 흐름으로 만든다.

## 화면과 경로

| 화면 | 경로 | 내용 |
| --- | --- | --- |
| 학습 홈 | `/student/learning` | 별명, 사실과 해석 안내, 서버 XP·레벨, 통과 회차/30, 첫 답변/150, 현재 행동, 30회차 목록 |
| 풀이와 해설 | `/student/learning/sessions/:sessionId` | 서버 세션의 현재 문항 또는 마지막 확정 해설, 제한시간, O/X 제출, 다음 문제, 마지막 `완료하기` |
| 결과 | `/student/learning/sessions/:sessionId/result` | GET으로 복원되는 완료 세션의 이번 정답 수, 통과/재도전/재학습/복습 결과, 누적 XP·레벨, 다음 행동 |
| 나의 문제 | `/student/questions?filter=REVIEW_QUEUE|MASTERED|BOOKMARKED` | 다시 볼 문제·복습 완료·별표 필터, 최근 상태, 별표 추가/해제, 큐 해제, 활성 큐 문항의 선택 복습 |
| 내 정보 | 기존 `/student/account` | 기존 학생 계정 정보·비밀번호 변경 접근 유지 |

학생 로그인 성공, 학생의 루트/로고 이동, 학생 비밀번호 변경 후 기본 목적지는 학습 홈으로 통일한다. 헤더에 `학습`, `나의 문제`, `내 정보`를 제공한다. 교직원의 기본 화면과 비밀번호 변경 강제 흐름은 유지한다. 모든 새 화면은 STUDENT 보호 경로다.

| U06 | 로컬 시간이 0이 되어도 정답/오답/timeout을 만들거나 자동 advance하지 않는다. `서버에서 답변을 확인하고 있어요`를 표시하고 현재 세션을 다시 조회하여 worker의 확정 결과를 복원한다. 탭 복귀·네트워크 복귀에도 즉시 재조회한다. |
| U07 | O/X는 한 논리 제출당 하나의 UUID `requestId`와 고정 payload를 사용한다. 빠른 중복 클릭을 동기적으로 막고, 응답 유실·CSRF 오류 후 명시적 재시도는 같은 ID/payload를 재사용한다. 답변·통과·XP를 클라이언트에서 낙관적으로 확정하지 않는다. |
| U08 | 불확실한 start/answer/advance의 최소 명령 정보는 학생 ID 범위의 sessionStorage에 보관하여 새로고침 후 복구한다. 비밀번호·정답·해설·남은 시간·XP 사실은 영속 클라이언트 저장소에 저장하지 않는다. 저장소 사용 불가/변조는 화면 전체를 중단시키지 않고 서버 세션 재조회로 복구한다. |
| U09 | QUESTION_ACTIVE는 문제·선택을, AWAITING_ADVANCE는 확정 해설·다음 문제를, COMPLETED는 마지막 해설·`완료하기`를 렌더링한다. 새 문제를 여는 동작은 명시적 advance만 수행한다. |
| U10 | 해설은 서버 outcome·correctChoice·explanation·xpAwarded를 그대로 표시한다. 정답/오답/시간 초과는 문구로 구분하고, 오답에도 원문 해설과 획득 XP를 표시한다. |
| U11 | 다섯 번째 답변 뒤 `완료하기`를 누르지 않고 나가거나 새로고침해도 결과가 복원된다. `완료하기`는 결과 경로로 이동하는 동작이며 결과 저장 POST를 추가하지 않는다. 결과 페이지에 아직 미완료인 세션으로 접근하면 현재 풀이로 연결한다. |

| U13 | 다음 회차 버튼은 새 status와 서버 날짜 상한/순차 상태로 결정한다. RETRY_REQUIRED는 5문항 전체 REPLAY, 통과한 과거 회차는 REPLAY다. 반복 보상·밀림 보상·레벨은 서버 값만 보여준다. |
| U14 | `reviewPromptEligible=true`인 해설에 `다시 볼 문제로 추가할까요?`와 `추가하기`/`지금은 괜찮아요`를 표시한다. 동의 때만 PUT한다. 사용자가 추가한 큐는 이후 정답으로 자동 제거하지 않으며 별표와 독립적이다. |

| U16 | 개인정보는 학생별 query key·취소 신호와 기존 계정 전환/401 cache clearing으로 격리한다. 로그아웃/학생 전환 뒤 늦게 도착한 이전 학습 응답이나 대기 명령이 새 계정에 표시·제출되지 않아야 한다. |
| U17 | 모바일 360px와 데스크톱에서 문항/해설이 잘리거나 가로 스크롤이 생기지 않는다. 48px 이상 터치 대상, 키보드 조작·보이는 focus, 색상 이외 판정 문구, 새 문항/해설 focus, reduced motion을 제공한다. 매초 카운트다운을 live announcement로 읽지 않는다. |

## API와 데이터 경계

기존 `LearningStatus`, `LearningSessionView`, `QuestionPrompt`, `AnswerResult`, `PersonalQuestionView`를 TypeScript 타입으로 대응시킨다. REVIEW의 `dayNumber`, `attemptState`, `dayState`가 null인 계약을 유지한다. status/session/private GET은 query 취소 신호를 전달하고, 모든 쓰기는 기존 세션 쿠키·CSRF helper를 통한다.

사용 API는 status/start/session/answer/advance, 세 개인 필터, review-queue 및 bookmarks PUT/DELETE다. 학생 식별자는 서버 principal이 정하며 UI 요청 본문에 학생 ID를 추가하지 않는다. 서버 정답·해설 데이터나 questions.json을 프런트엔드에 복사하지 않는다.

현재 완료 세션 GET은 마지막 결과와 시도 정답/답변 수·누적 XP·레벨을 제공한다. 전체 시도의 XP 합계나 다섯 문항의 개별 결과 배열은 제공하지 않으므로 그런 수치를 만들어 표시하지 않는다. 해설에서 `xpAwarded`를 `이번 답변으로 받은 경험치`로 표시하고, 결과 요약은 서버 정답 수·누적 XP·레벨을 사용한다.

개인 목록 DTO에는 첫 outcome·정답·해설·큐 등록 reason이 없으므로 임의로 추정해 표시하지 않는다. 별표한 미답변 문제를 포함한 목록에 사전 해설 보기 기능을 만들지 않는다. 큐에 없는 복습 완료/별표 문항을 REVIEW로 시작하는 우회도 만들지 않는다.

## 복구와 오류

- 연결 실패는 원문 오류/요청을 로그에 남기지 않고 한국어 오류와 명시적 재시도를 제공한다. 성공이 불확실한 쓰기의 ID를 새로 생성하지 않는다.
- ANSWER_ALREADY_FINALIZED/QUESTION_MISMATCH는 GET으로 확정 상태를 복원한다. SESSION_CONFLICT는 status의 활성 세션으로 이어갈 수 있게 한다. IDEMPOTENCY_KEY_REUSED/CONTENT_VERSION_MISMATCH는 재조회 안내와 안전한 홈 이동을 제공하고 무한 자동 재전송을 하지 않는다.
- HTTP 401은 기존 로그인 화면으로 연결하며 이전 학생 캐시와 UI 대기 상태를 제거한다. 404 세션은 다른 학생 데이터 없이 찾을 수 없음·홈 이동을 제공한다.
- start/advance snapshot이 이미 오래된 상태면 응답을 현재 세션 GET과 조정한다. 아직 확정되지 않은 문제에 과거 lastAnswer를 붙이지 않는다.
- 만료 확정 대기 poll은 해당 활성 세션에만 걸며 확정/화면 종료/계정 전환 시 중단한다. 해설을 읽는 동안 다음 문항 타이머를 시작하지 않는다.

## 스타일과 구성

기존 CSS 토큰 `#fffdf3`, `#fffef9`, `#f4d66e`, `#263d35`, `#e2dec9`, 한국어 시스템 폰트와 카드 형태를 재사용한다. 문제는 읽기 쉬운 720px 내외 본문 영역과 크게 구분된 O/X 버튼을 사용한다. 홈의 핵심은 오늘 할 수 있는 행동 하나이며 30회차 목록·개인 목록은 보조 영역이다. 회차는 `일차`보다 `회차`로 표현하여 밀린 순차 학습과 날짜를 혼동시키지 않는다.

`features/learning` 안에서 타입/API·조회·대기 명령/복구·서버 시계·홈·세션·결과·개인 목록·학습 스타일을 책임별 파일로 나눈다. 기존 공용 HTTP와 auth/router 수정은 이 흐름에 필요한 작은 확장만 한다. 새 UI 의존성은 추가하지 않는다.

## 검증과 배포

Vitest/MSW는 역할/랜딩, status 행동표, 안전한 prompt, 세 phase, deadline 재개·기기 시계 변경, 응답 유실 뒤 동일 ID, 빠른 중복 클릭, 오류/CSRF/계정 전환, 다섯 번째 저장, 개인 목록/동의를 검증한다. 컴포넌트 자체를 모의 구현하지 않고 실제 페이지와 HTTP 경계를 사용한다.

별도 `hanbit-account-e2e` Compose DB의 실제 계정·학급·학생과 PostgreSQL로 Chromium 흐름을 검증한다. 첫 통과, 2/5 실패 후 REPLAY 통과, deadline 유지/timeout 복원, 큐와 별표, 결과 재로그인 복원을 포함한다. 테스트용 자격 증명은 기존 ignored E2E 환경과 메모리에만 두고 일반 로그·trace·영상·스크린샷에 남기지 않는다.

운영 재배포는 현재 `hanbit-prod` Compose, Cloudflare Tunnel, DB 볼륨을 보존한다. 이번 UI 계획에는 운영 schema migration이 필요하지 않다. 배포 전 DB backup, 이미지 build, 서비스 교체/상태, 외부 로그인·API·자산, 실제 화면을 확인하고 실행 증거를 기록한다. 운영 검증에 새 테스트 계정/학습 행이 필요하면 별도 검증용 학생임을 표시한 합성 데이터만 사용하며, 사용자 기존 계정·학습 결과는 변경하지 않는다. 실브라우저 전체 풀이의 주 검증은 격리된 E2E 환경에서 수행한다.

기능 브랜치는 `feat/student-learning-ui`, 작업 단위 커밋을 분리한다. 사용자가 지정한 실행 방법은 `subagent-driven-development`이며 설계/계획 승인 후 새 구현자와 독립 reviewer를 task별로 배정한다. 최종 branch review와 검증 후 사용자 요청대로 같은 운영 링크에 배포한다.

## 설계 자체 검토

- U01~U18은 목적의 로그인 후 실제 풀이, 복원, 개인 목록, 검증/배포에 직접 연결된다.
- 서버의 날짜·정답·XP·마감·마스터리 권한을 UI로 옮기지 않는다.
- API에 없는 결과 합계/배열·개인 목록 첫 outcome/정답/해설을 표시하지 않는 경계를 명시했다.
- 승인된 반복 1 XP, 밀림 최종 지급액 -1 XP, 3/5 통과, 5번째 자동 저장, 수동 큐 유지와 모순이 없다.
- 이번 검토 대상은 UI 설계이며, 승인 후 파일/인터페이스/이름 있는 테스트/커밋 단위 구현 계획을 작성한다.
